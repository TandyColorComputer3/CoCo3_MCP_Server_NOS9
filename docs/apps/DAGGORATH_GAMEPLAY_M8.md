## 1. Original heartbeat audio and visual trace

`PLOOK.ASM:INIVUX` clears status/text, calls `HUPDAT`, increments `HEARTC` so the first enabled heartbeat is due immediately, enables `HEARTF` (visual) and `HBEATF` (single-bit output), then draws `STATUS`. In `COMMON.ASM:CLOCK/CLK30`, a video interrupt decrements `HEARTC`. Only when it reaches zero does the routine reload from `HEARTR`, toggle PIA1 port B bit 1, and, **in that same interrupt after the output toggle**, check `HEARTF`. If enabled, it complements `HEARTS` and writes the left/right glyph pair into `TXTSTS` columns 15–16 through `TXTDPB`, preserving the text cursor. `CD.ASM` names the four glyphs `I.SHL/I.SHR` and `I.LHL/I.LHR`; `SWCHAR.ASM:SPCTAB` supplies their seven-row pixel data. With cleared `HEARTS`, the first complement selects the **large** pair, then small, alternating once per output edge. A disabled `HEARTF` omits that drawing; it does not change the `HBEATF` countdown/output path. `HUPDAT.ASM:HUPDAX` calculates the delay from power and damage and writes `HEARTR`; it does not reset the active `HEARTC`, so a changed rate takes effect at the following reload. The heartbeat is the native held-level PB1 transition, not a separate short synthesized tone. [Audio M3](DAGGORATH_AUDIO_M3.md) has the original edge and PCM investigation.

Healthy `HEARTR` is 46 video ticks in the validated initial state; the damage-dependent formula in `HUPDAT` can shorten it, with a three-tick fast case already tested for the native driver. Avoid treating these as a fixed two-beat audio sample: every PB1 transition changes the held level, and the source toggles the heart shape at that transition **while `HEARTF` is enabled**. With `HEARTF` disabled, `HEARTS` does not advance even though the audio edge can still occur; future map/view behavior must preserve that distinction rather than equating the native output-phase latch with every historical display mode. Original `COMMON.ASM:CLOCK` writes the glyph to the game text buffer during IRQ service. Physical scanout still occurs when the video system scans the changed memory; `PUPDAT.ASM:PUPDAX` and the `UPDATE` flip mechanism can affect which buffer is displayed. The inspected source establishes update order, **not a measured upper bound** on when a viewer saw each shape. No claim is made that a host screenshot is simultaneous with the PIA edge.

### Current port versus the actual gap

This coupling is **already implemented**, so M8 must not create a second visual timer. M2 added the phase latch; M6 added the atomic read-only `$96` phase plus 32-bit edge-generation snapshot to `DHeartbeat` (`apps/daggorath/src/audio/native/driver.asm:tick/snapshot`). The callback toggles `$FF22` bit 1, then the phase and generation, reloading `remaining` from `rate`; `$92` changes only the future rate, `$94` freezes, and `$93` resumes without resetting phase/countdown. `game_render_status` uses the imported `SPCTAB` small/large pair; `gameplay/main.c` samples the native phase after expensive scene work, repacks the 15 status/input rows, presents, and checks whether an edge arrived during the transfer. The main loop refreshes on pending generation/phase. Audio keeps its VIRQ deadline independently of foreground drawing.

The unsolved part is **visual latency**, not an absent phase relationship. In accepted M6 samples, all observed native edges met their countdown deadlines and callback gaps were about 16.56–16.83 ms. Presentation can lag: one cancellation sample generated four physical edges but presented generation three before teardown. An illuminated full redraw took about 4.35–4.39 s, with approximately 3.95 s in logical scene generation alone. That can skip several visual alternations while audio continues. A single present of the latest phase is correct catch-up state, but cannot recreate missed visible alternations. Do not call this zero visual drift or promise perceptual synchrony under that redraw cost. M6's paired native-edge/presentation evidence is in its [timing section](DAGGORATH_GAMEPLAY_M6.md#live-qten-heartbeat-and-runtime-disk-measurements).

**Proposed synchronization/presentation work:** retain one VIRQ-owned `(countdown, rate, PB1 level, phase, generation)` record. Keep the glyph pair a pure render of the latest atomic snapshot; never increment it in gameplay or replay missed edges. Split long *foreground* scene preparation at source-safe rendering boundaries so the process can yield, check phase/generation, and update the already displayed status region before continuing. The currently displayed image must remain valid while a new logical scene is prepared; define buffer ownership before changing the renderer. Preserve the original 256×192 logical image and 512×192 presentation. Measure the cost of each slice and full upload before setting a visual-latency acceptance bound. Shortening a draw by busy-waiting, masking interrupts, or putting graphics in the VIRQ is forbidden. If a separate status update cannot be made safely while the scene is partial, retain the present implementation and document the measured limitation rather than display torn game pixels.

## 3. Future mouse, menu, and view boundary

One owned 640×200 graphics screen remains the presentation surface. A future UI controller can have `menuHidden`, last-motion time, and selected view as **presentation state**, separate from authoritative `Game`/OCB/CCB state and the native heartbeat counter. Mouse motion would reveal the menu; subsequent motion keeps it visible; after approximately two seconds of no motion, the controller hides it on a cooperative foreground update. It must use an elapsed-clock deadline, not a stream of extra sleeps that delay game/keyboard service. The menu overlay and its erasure must preserve/repaint the pixels beneath it, including the viewport and status strip. None of this changes Q.TEN, PB1, or heartbeat generation.

Verified API candidates: upstream `defs/os9.d` names `SS.Mouse`, `SS.MsSig`, `SS.WnSet`, `SS.MnSel`, `SS.SBar`, `SS.UMBar`; `level2/coco3/modules/vtio.asm:GSMouse/SSMsSig` copies a 32-byte mouse packet and can signal on **button** events, and `cowin.asm:L1515` implements menu selection. `defs/cocovtio.d` defines `Pt.AcX/Pt.AcY/Pt.Stat`. EOU GFX2 and the [recovered MVKit references](../reference-projects/MVKIT_RECONSTRUCTION.md) show event/menu plumbing. **Mouse-movement signals and an `OnMouse` API with the desired hide/reveal semantics have not been verified.** `SS.MsSig` alone must not be treated as a motion notification. A bounded future prototype must establish the EOU mouse packet, movement observation/cadence, pointer visibility, menu selection, and cleanup on the owned window before adopting any exact packet layout or signal code. Do not poll PIA/joystick hardware directly. MVKit is a pattern source, not a required visual style or a certified EOU runtime library.

Future view roles are `gameplay`, `sidebar map`, `sidebar inventory`, `large map`, and `large inventory`, with an explicit return to canonical gameplay. Each is a renderer of authoritative maze, OCB, CCB, player, and inventory state. The 512×192 viewport at `(64,4)` remains canonical; each 64-pixel side strip is reserved, not a separate `/w` process. A larger map/inventory view may temporarily occupy the same owned screen, but may not maintain a second divergent game model. View switching must preserve ongoing audio/Q.TEN deadlines, keyboard ownership, and a route back to gameplay. This is an architectural boundary only: no enhanced map, inventory view, mouse menu, or side-panel content is implemented at this checkpoint.

## 4. SSC sword, spider, and snake acceptance status

Original source is specific. `SOUNDS.ASM:SNDTAB` maps spider type 0 `A$SQK0 → SQUEAK` and viper type 1 `A$RTL0 → RATTLE` (the source's snake-like rattling effect; scorpion type 6 instead maps `A$RTL1 → PSSST`). Sword **swing** is object class `K.SWOR + SNDOBJ` through `PATTK.ASM:PATT10`, giving `A$SWOR → WHOOSH`, a noise/envelope effect. A successful hit on a creature then calls `ISOUND A$KLK2 → KLINK` (`PATTK:PATT24`), whose source mixes high-pitched tone and noise with a decay envelope; a creature's successful hit on the player uses `A$KLK3 → CLANK` (`CRETUR:CMOV20..30`). These are distinct semantic events. Creature movement near the player may request its type sound through `CRETUR:CWALK`; same-cell `CMOV20` requests the creature type sound before shield/attack resolution. All original routines output through the six-bit DAC path; this does not identify an equivalent SSC recipe.

## 5. `CMOV20` combat order and proposed first slice

`COMCRE.ASM:CBIRTH` queues `CRETUR.ASM:CMOVE` at `P.CCTMV` on `Q.TEN`. `CMOV10` may pick up an object and postpone other behavior. `CMOV20` checks **same row and column**, not ranged attack or a separate proximity threshold. If not same-cell, `CMOV50..78` handles sight/movement (already M6). At same-cell it requests the creature's type sound at full volume, initializes minimal magical/physical defense `$8080`, examines both held objects through `SHIELD` (only shield-class OCBs can upgrade that defense), stores `PMGD/PPHD`, and calls `PATTK.ASM:ATTACK` with creature as attacker and player `PLRBLK` as defender. `ATTACK` uses attacker power, defender power minus damage, a percentage-index calculation, and `RANDOM` to decide hit/miss. On hit, `CMOV20` requests `A$KLK3` and calls `DAMAGE`; `PATTK:DAMAGE/SCAL16` applies magical and physical components to `PDAM` and compares damage with player power. Hit or miss then reaches `CMOV30`, calls `HUPDAT`, and schedules the next attempt using `P.CCTAT` via `CMOV92/98`. `HUPDAT.ASM:HUPDAX` changes `HEARTR` from `PPOW/PDAM`, may trigger faint/death display behavior, and **does not reset the current `HEARTC`**. A landed hit can therefore change the **next** heartbeat interval after the current countdown expires; it does not independently flip the visible heart immediately. `PUPDAT`/status changes occur through the corresponding display paths, not through an invented attack-frame timer. Player-initiated `PATTK` is a separate branch with object-swing sound, exertion damage, hit checks, creature damage/death and loot; do not bundle it into the first creature-hit slice merely because it uses `ATTACK/DAMAGE`.

The smallest plausible first combat implementation, **after this checkpoint and the heartbeat/window gates**, is one source-ordered same-cell creature attack transaction: verified eligibility; both-hand shield selection; exact RNG/hit arithmetic; damage; `HUPDAT` rate effect; attack-delay reload; and required status/scene consequences. Keep sound as a semantically identified event with an explicit unavailable/validated backend policy rather than silently claiming sword/viper fidelity. Whether source-ordered audible creature and CLANK playback must block the transaction remains a test decision: original `SOUNDS` is synchronous, while SSC service is asynchronous. A cartridge oracle must resolve the state/action ordering before production code changes. Exclude player attack, creature death/loot, full combat, new game commands, new creature types, and future-level population.

### Knight warning cue listening follow-up

The user's remembered metallic dragging warning was absent from the first five clips. `SOUNDS.ASM:SNDTAB` identifies a separate `A$KLK0 → KLANK` for knight 1 and `A$KLK1 → KKLANK` for knight 2. `CRETUR.ASM:CWALK` can request a nearby moving creature's type cue; `CMOV20` requests it at a same-cell encounter. These differ from `KLINK` (player hits a creature) and `CLANK` (creature hits player). The original table calls types 2 and 5 stone giants, with `GROWL` and `GRAWL`; it does not label them ogres.
