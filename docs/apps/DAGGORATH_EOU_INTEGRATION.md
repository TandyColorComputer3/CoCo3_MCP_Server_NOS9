## Application and GShell ownership

**VERIFIED FROM DOCUMENTATION/SOURCE:** GShell 1.0.0/1.0.1 is a window-launching shell, not merely an icon picker. The transition guide pp. 6–8 says an AIF specifies launch screen type and minimum size; full-size requests launch directly, while smaller requests can be positioned/sized, potentially on an existing screen of the same type. GShell source `ICONAIF → EXECAIF → EXCICOND → ISCR512K/FORKPROC`, plus `NEWSTDIO`/`RESTDIO`, shows the intended division: GShell creates/selects a child window, duplicates that path into standard input/output/error for the fork, tracks child PID/status, waits, and reestablishes its own paths. `ISCR512K` distinguishes full-screen from resizable requests. A same-AIF live probe measured W3 on all three child paths and PID 4 under parent 3; the game trace below separately identifies its own local path 3.

**VERIFIED FROM DOCUMENTATION/SOURCE:** The AIF is launcher metadata, not game logic. GShell `ID.MNAME`, `ID.PARAM`, `ID.MEMSZ`, `ID.WTYPE`, `ID.XSIZE`, `ID.YSIZE`, `ID.BKGND`, `ID.FRGND` are populated in `FILE.XXX` from its nine CR-delimited lines. Line 1 may use `module|display name` (transition guide p. 31); line 2 supplies or prompts for parameters; line 3 names the icon file. The source contains a *commented proposal* for future default data/execution directory fields, **not an implemented line 10/11 contract**. Therefore a Daggorath installer must not assume that an AIF changes the child's working directory. The actual child data/execution directory inheritance and any EOU 1.0.1 extension need a live launch check.

**Real EOU file example, verified by read-only image inspection:** `/dd/GAMES/LEVEL2/ARCADE/BONK/AIF.bnk` contains nine CR-separated values: `Bonk`, empty parameters, `ICONS/icon.bonk`, `0` memory modifier, type `1`, `40`, `25`, background `0`, foreground `2`, followed by a final `2` whose meaning was **not established** by the inspected nine-line parser. `/dd/CMDS/bonk` exists (BASIC09 I-code module, edition 14, CRC `0BB25D`), and `/dd/CMDS/ICONS/icon.bonk` is the associated icon namespace. `/dd/APPS/AIF.gcl` uses `GCal|GCalendar` and `icons/icon.calendar`; `/dd/CMDS/ICONS/icon.calendar` is 144 bytes. The source reads a 144-byte icon buffer (`FILE.XXX`), and the listed EOU icons are 144-byte resources. This traces actual installed *files* and parser fields; it does not prove a successful current-runtime click-through to Bonk or GCal. `AIF.xxx` can describe an extension association or stand as an icon entry in the directory; GShell's `FILE.XXX`/`FPTR.XXX` handles these paths. A future Daggorath AIF name/placement must be proven with a disposable install test.

**VERIFIED FROM EOU SOURCE:** `gshell_ver1_0_1.asm:SET24X24` calls the ordinary 144-byte AIF icon a **24×24, four-color** buffer, and `ICN48X24`/`SR48X24` expand each source pixel horizontally for a **48×24** buffer in 80-column mode. `FILE.XXX` reads the 144-byte icon, then loads the ordinary and expanded buffers. This establishes a source-derived two-bit-per-pixel ordinary resource with GShell-generated wide presentation; the installed binary's exact palette mapping and whether any separate 640-mode thin resource is selected remain **UNKNOWN** without a source/runtime match or the 1.0.1 release notes. Installed examples use `ICONS/icon.*`. SuperIke 1.1 is listed by the EOU transition/release documentation, and `/dd/SOURCECODE/BASIC09/SUPERIKE/superike.b09` uses GFX2 Title/Menu/Item/WnSet/OnMouse/GetSel, but it does not determine the final Daggorath icon design.

## Window policy for the current and future game

**VERIFIED LIVE and SOURCE:** The current game checks `SS.ScTyp` and matching `SS.DevNm` on inherited input/output, opens its **own** `/w`, issues `DWSet` type 5, verifies type 5 and 80×25 cell working area, selects its window, and later selects the caller's window and closes only its own resources. Prior EOU tests show normal Term and an existing type-5 `/w3` shell both launch, exit to their original prompt, and permit strict commands; mismatched Term input and `/w2` output returns 187 before graphics. The new GShell checkpoint shows a game screen and visual return, but did not directly inspect its inherited paths or allocated window. Type-1 40×25 descriptor attributes were queried, but a game launch from that shell remains unverified ([M8 window matrix](DAGGORATH_GAMEPLAY_M8.md); `apps/daggorath/src/presentation.c:invocation_window/screen_open/screen_close`). The technical reference Chapter 9 `SS.ScTyp` identifies type 1 as 40-column text and type 5 as 640×192/200 two-color graphics. `SS.ScSiz` is a *cell working-area* query, not a 640×200 pixel query.

The canonical content remains **one owned 640×200 type-5 graphics screen**: `x=0..63` future left reserve, `x=64..575` 512×192 game, `x=576..639` future right reserve; game pixels begin near `(64,4)` and derive from the unchanged 256×192 logical frame with 2× horizontal expansion. This is the already tested port contract, not a new window experiment. It does not imply separate `/w` windows for the three regions.

**Important unresolved ownership choice:** If GShell has already allocated a suitable full-screen type-5 child window, opening another full-screen `/w` may waste graphics memory and create selection-order surprises. Reusing the inherited GShell window would avoid that, but would require proven rules for screen contents, palette, cursor, keyboard mouse, signals, select-on-exit, and whether GShell or the child closes the path. The current ownership model remains the accepted safe baseline until the GShell live matrix resolves this. The preference that an unsuitable caller can still obtain suitable graphics is met for ordinary matching Term and `/w` paths by the current owned-window approach; arbitrary redirection is deliberately rejected.

## Mouse and scheduling

**VERIFIED FROM DOCUMENTATION/SOURCE:** Technical Reference Chapter 9 `SS.Mouse` GetStat `$89` returns a 32-byte packet. Relevant fields are `Pt.Valid` at 0 (zero if not the current interactive window), button state at 8–9, `Pt.Stat` at 0x16 (working/menu/off-window), `Pt.Res` at 0x17, actual coordinates at 0x18/0x1A, and window-relative coordinates at 0x1C/0x1E. The same code as SetStat controls sample rate and timeout in 60 Hz ticks, plus CoWin auto-follow. `SS.MsSig` SetStat `$8A` requests a **one-shot mouse button-press signal**; it must be rearmed. `SS.Relea` clears pending keyboard/mouse signal requests. The transition guide and [EOU Beta 5 release description](https://lcurtisboyle.com/nitros9/nitros9_docs.html) say keyboard mouse state became window-local; the packet's `Pt.Valid` rule matters when the game switches screens.

`gfx2_ver1.asm` maps BASIC09 `Mouse` to `SS.Mouse` GetStat (five- or eight-argument form), `SetMouse` to `SS.Mouse` SetStat, `GetSel` to `SS.MnSel`, and `OnMouse` to both `SS.MsSig` and `SS.SSig`. With its zero parameter, `OnMouse` uses `S$Wake` and `F$Sleep` until **button or key**, then releases the requests. `/dd/SOURCECODE/BASIC09/SUPERIKE/superike.b09` lines around `RUN gfx2("SetMouse",3,1,1)` and `RUN gfx2("OnMouse",0)` are a concrete application use. **No inspected API delivers a signal on mere pointer movement**; treating `OnMouse` as movement notification would be wrong. Exact button/keyboard races and mouse cursor drawing in the currently installed CoWin remain **NEEDS LIVE TEST**.

**Recommended event foundation (STRONG INFERENCE):** Let the ordinary game scheduling loop take a bounded `SS.Mouse` sample at a modest tick interval when its owned screen is interactive, compare valid window-relative coordinates/buttons to the previous valid packet, and set `menu_hide_deadline = last_activity_tick + ~120` for a two-second grace period. Use the existing game wait/yield opportunities and one-shot button/key signals for prompt wakeups. Do not poll at audio rate, spin while idle, change global mouse side (`SS.GIP`), or route mouse work through the heartbeat VIRQ. The native heartbeat remains the independent timing authority. A concrete sampling cadence, keyboard coexistence, and handling of `Pt.Valid=0` require an EOU live test; the ~120-tick deadline follows the documented 60 Hz timebase, **not** a measured menu implementation.

## Native menus versus a transient game overlay

**VERIFIED FROM DOCUMENTATION/SOURCE:** Technical Reference Chapter 9 `SS.WnSet` SetStat `$86` sets a high-level CoWin window *after* `DWSet`/`OWSet`; its descriptor is `WN.*`/`MN.*`/`MI.*` (`/dd/defs/cocovtio.d`). `SS.MnSel` GetStat `$87` is called after a valid control-area click and returns menu ID in A and item in B; an itemless menu yields B=0 for application-specific drawing. `SS.UMBar` SetStat `$95` redraws the menu bar after menu changes/pull-down completion. `SS.SBar` SetStat `$88` positions **scrollbar markers** for framed scrolling windows; it is not an API for Daggorath's side panels. `gfx2_ver1.asm` implements BASIC09 `Title`, `Menu`, `Item` by filling these descriptors, `WnSet` by `SS.WnSet`, `GetSel` by `SS.MnSel`, and `UMBar`/`SBar` by corresponding SetStats. SuperIke source uses those calls as a real menu application. The technical reference identifies `MVCanvas` as an example of an itemless title triggering application-owned pull-down graphics.

**UNKNOWN:** The available manuals/source do not establish a documented call that toggles a framed CoWin menu bar on for pointer activity and removes it two seconds later **without changing the child window's working area or damaging the mapped Daggorath image**. `SS.UMBar` means redraw/update, not necessarily hide. The exact pixel save/restore behavior of native pull-downs on this EOU build was not measured. We therefore cannot promise a native hidden menu or zero redraw yet.

**Recommended design candidate (STRONG INFERENCE, not implemented):** Keep gameplay in its owned type-5 full-screen window. Make the transient chrome application-owned pixels in a small reserved/overlaid region of the *presentation* buffer, with an explicit save/restore or deterministic recomposition step; leave the 256×192 logical game and the native heartbeat untouched. If a future live CoWin experiment establishes that `SS.WnSet`/`SS.MnSel` supports reversible transient menus on this screen with safe buffer restoration, use native menu selection for Game/View/Options/Help and app-owned pixels only for appearance. The four top-level names are product concepts, not a finalized menu tree. The game image starts at y≈4, so even an 8-pixel bar overlaps it unless a presentation-region policy is established. Do not just draw over the mapped image and assume the underlying game pixels survive.

MVKit's event/menu abstractions (see [reconstruction](../reference-projects/MVKIT_RECONSTRUCTION.md)) are useful design examples, but its framed-window assumptions and cleanup are not a verified EOU abstraction for this game. It need not be adopted to obtain a menu.

## Side panels, alternate views, and 6309 hotspots

**STRONG INFERENCE grounded in the existing renderer:** One owned 640×200 screen naturally accommodates left `0..63` and right `576..639` presentation regions outside the 512×192 game rectangle. An application-owned compositor can place map/inventory/status pixels there while leaving the logical game buffer and coordinates untouched. A 64-pixel panel is narrow; font legibility, content density and cost remain **UNKNOWN**. Alternate full-window map/inventory could be a view rendered into the same owned screen and then restored, or a separately owned `/w`; neither navigation/ownership contract is yet tested. `SS.SBar` does not create these regions. Any buffer selection or overlay must preserve the current exact-frame gameplay and heart presentations. No panel is implemented here.

**VERIFIED FROM SOURCE:** The pinned upstream `level2/cmds/grfdrv.asm` has 6309 `TFM`/`LDQ` paths for graphics copies/PutBlk and comments that performance can differ by operation; its clear-screen comment near line 1033 even says TFM has less than 150-cycle advantage over an alternative for a 32 KB screen. The EOU GShell source contains 6309 notes and unfinished optimization comments. **STRONG INFERENCE:** candidate application hotspots are the port's nibble-to-doubled-bit 2× expansion, mapped-buffer line copies, narrow status/heart refresh, and future menu/panel save/restore. `TFM` is suited to contiguous copies; it does not alone perform bit expansion, so a table-driven expansion or measured assembly loop may matter more. `LDQ/STQ` might help aligned 4-byte moves where ABI/packing permits. First measure per-stage latency, bytes moved and CPU occupancy under the existing native heartbeat. Any optimization belongs in the foreground presentation boundary, never in a long interrupt mask, busy wait, or replacement heartbeat clock.
