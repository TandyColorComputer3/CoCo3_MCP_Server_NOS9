# Gameplay M7 archaeology and scope gate

**Status: stopped before implementation.** The next unported part of the active creature path is the same-cell attack body. A faithful unit there depends substantially on combat, which this request excludes. M6 already implements the separable creature scheduling, object pickup, sight, movement, collision, and visibility path. No M7 production code, fixture, cartridge capture, or live acceptance result is claimed here.

## Evidence and original execution order

Primary source is the read-only Dungeons of Daggorath checkout at `/Volumes/SEDONA/Projects/daggorath-reference`, commit `a94326f00ebb16a106b540c58bc2ccf5f7b66dac`. The existing [M6 report](DAGGORATH_GAMEPLAY_M6.md) and `apps/daggorath/src/gameplay/` establish the port boundary. Paths and labels below refer to that exact cartridge source. `MCP/Documents/` and `DOCS_INDEX.md` are absent from this checkout; no manual-based claim is added.

1. `ONCE.ASM:SYSTCB` initializes the task queues and puts `COMDAT.ASM:TCBDAT` tasks in the runnable queue: `PLAYER`, `LUKNEW`, `HSLOW`, `BURNER`, and `CREGEN`. `ONCE.ASM:GAME20` invokes `NEWLVL`; `NEWLVL.ASM:NLVL30..34` calls `COMCRE.ASM:CBIRTH` for the level population. `CBIRTH` fills each CCB and queues its `CMOVE` task using its `P.CCTMV` delay on `Q.TEN`.
2. `COMMON.ASM:CLOCK/CLK40..50` processes the jiffy queue on each video interrupt. `ROLTAB` rolls six jiffies into one `Q.TEN` unit, then ten tenths into a second. `QUESCN` decrements queued TCB timers and moves expired tasks into the scheduler queue. `COMMON.ASM:SCHED/SCHED1` dispatches runnable tasks; each task returns its next queue and delay. The IRQ produces deadlines; gameplay routines run in the scheduler, outside the interrupt.
3. While the player waits, `HUMAN.ASM:PLAYER/PLAY10` drains available keyboard characters through `KBDGET` and `HUMAN`. On an empty buffer, `PLAY99` schedules the next check one jiffy later. `HUMAN:HMAN20..70` echoes/buffers characters, dispatches on carriage return through `PARSER` and `DISPAT`, and then prompts unless map/faint state suppresses it. The cartridge clock and creature tasks continue while no player command is entered. A player command uses foreground scheduler time to execute but does not itself generate a separate `Q.TEN` tick.
4. `CRETUR.ASM:CMOVE` runs when its `Q.TEN` countdown expires. `CMOV10..12` may pick up a floor object. `CMOV20` compares creature and player coordinates. If equal, its next instructions call `SOUNDS`, derive hand/shield values via `SHIELD`, invoke `ATTACK`, conditionally invoke `DAMAGE`, update the heartbeat through `HUPDAT`, and select the attack delay at `CMOV92`. If coordinates differ, `CMOV50..62` tests axis-aligned sight, `CMOV70..78` chooses a random movement sequence, and `CWALK/STEPOK/CFIND` attempt a legal unoccupied step. `CMOV90/98` selects the next movement or attack countdown. Distance and random state also govern the near-creature sound request in `CWALK`.
5. Visibility is derived from the current CCBs in `VIEWER.ASM` through `COMCRE.ASM:CFIND`, which requires `P.CCUSE` to mark the record active. `COMPLR.ASM:LUKNEW` services requested delayed display updates every three `Q.TEN` units; `CRETUR:CWALK` sets `NEWLUK` near the player, and a same-cell encounter forces `PUPDAT`. `PUPDAT.ASM:PUPDAX/PUPSUB` rebuilds the selected view and requests a screen flip. These are presentation consequences of already-modeled CCB movement, not a separate creature behavior.
6. Other periodic game work is `COMPLR.ASM:HSLOW` damage recovery and heart-rate update, `BURNER` torch fuel/light updates once per minute, and `COMCRE.ASM:CREGEN` every five minutes. `CREGEN` increments one entry in the current `CMXPTR` population matrix when its count is below 32. It does **not** call `CBIRTH`; the extra creature is instantiated only by a later `NEWLVL` level rebuild. The port already has a bounded `game_tick` path for recovery and torch aging. Implementing `CREGEN` alone would create no new resident creature behavior or visible M7 result and would depend on unported level-transition semantics for its effect.
7. `COMMON.ASM:CLK30` owns the original heartbeat output and status-heart flash on the video interrupt; `PLOOK.ASM:INIVUX` enables them. `HUPDAT` changes heart rate from player state without creating a second clock. Creature attack can change damage and hence the heartbeat through `HUPDAT`; movement alone does not require that player-damage path.

## What the port already provides

The accepted M6 implementation uses native VIRQ tick accounting, converts each six video ticks to a creature `Q.TEN` step, and runs `game_creature_advance` in the foreground loop. `creature.c:move_one` implements object pickup, sight, movement, occupancy, original RNG use, and CCB updates. `main.c` renders those CCBs and keeps the native heartbeat callback short. At same-cell contact, it records `combatPending` and reloads the attack countdown but does not execute the cartridge attack body. The M6 report verifies exact 544-byte initialized CCB comparison, sampled Q.TEN accounting, heartbeat deadlines, lifecycle, and zero watched resident FDC accesses. It also records foreground redraw delays; these are pending-service/presentation latency, not a new game timer to replace.

| Original branch or task | After M6 | M7 scope consequence |
|---|---|---|
| `CMOVE` pickup, movement, sight, `CWALK`, CCB visibility | Implemented | Repeating it would not add a new subsystem. |
| `CMOV20..30` same-cell encounter | Gate/countdown only | Next executable body is sound, shield, attack, damage, heart-rate update. |
| `CWALK` near-creature sound | RNG call retained; sound omitted | New effect mapping belongs to audio work excluded here. |
| `CREGEN` population matrix | Not implemented | No immediate birth; needs a level rebuild to become observable. |
| `LUKNEW` delayed update | Port redraws from current CCB state | A rendering cadence change would not supply missing active creature semantics. |
| `HSLOW`, `BURNER`, heartbeat | Existing bounded equivalents | No independent post-M6 creature unit. |

## Boundary decision

There is no source-supported, self-contained **new** active-creature/time subsystem between M6's implemented movement branch and `CMOV20`'s combat branch. Selecting a smaller movement test, an inert `CREGEN` matrix increment, or a display-only refresh change would not satisfy the requested coherent gameplay milestone. Selecting `CMOV20` would require the excluded combat/damage work. This meets the request's explicit stop condition: **the next substantive subsystem depends substantially on combat**.

No cartridge-oracle scenario is fabricated for an unselected feature. The existing M6 initialization fixture and live comparisons remain the current evidence; they do not establish post-contact original-versus-port equivalence. Likewise, no M7 Q.TEN, heartbeat, FDC, lifecycle, screenshot, module CRC, or regression result is reported. An eventual combat milestone should first define its own bounded source-derived encounter/attack contract and capture a controlled cartridge state across `CMOV20`, including player/creature/hand/OCB state and exact scheduler timing. Level regeneration would require a separate level-transition contract and oracle. Neither is implemented here.
