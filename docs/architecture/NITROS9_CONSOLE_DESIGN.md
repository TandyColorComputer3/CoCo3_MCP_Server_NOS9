# NitrOS-9 console control: Milestone 1 design

Status: proposal only, 2026-09-25. No implementation or boot-image changes are included. The [architecture audit](CURRENT_ARCHITECTURE.md), [bridge trace](MAME_BRIDGE_FLOW.md), and [gap analysis](NITROS9_GAP_ANALYSIS.md) describe the current code. MCP/Documents/ and DOCS_INDEX.md are absent from this checkout, so OS-9 shell syntax, process behavior, device names, and boot semantics must be checked against primary manuals and a chosen boot image before being encoded.

## Desired contract

The milestone should distinguish six observable events: MAME/Lua connected; NitrOS-9 booted; the intended shell or login session ready; one command accepted; its output and completion observed; and recovery completed after a timeout. The current coco_start ping establishes only the first event. The current coco_type waits for MAME's keyboard queue to drain, not for command execution, and coco_snapshot returns pixels rather than text. [Source: tools.ts:226-249, 315-369](../../MCP/src/tools.ts).

A reliable command session needs one owner, a unique command ID, explicit start/end boundaries, a bounded timeout, and a response that distinguishes completed, timed out, transport lost, and guest reset. An exit status should be returned only if a verified guest shell or helper can supply it. Otherwise completion and output can be reported without inventing a status code. This is a proposed contract, not a claim about existing OS-9 shell commands.

## 1. Keyboard injection plus screen observation

Reuse coco_type and coco_snapshot. Boot readiness can be detected only from an observed guest-specific screen condition, not from Lua ping or keyboard-idle. A command might be bracketed by unique guest-visible markers if the chosen shell can emit them; that syntax is unverified here. Output could be read with OCR or a screen decoder tied to a verified video mode. Screenshots preserve what is visible at capture time, so long output and interleaved processes can defeat reconstruction. Fixed prompts alone can be matched accidentally inside command output.

This has the smallest initial guest footprint and provides a useful bootstrap, smoke test, and visual recovery check. It should not be the sole success criterion for a reliable general command API. MAME documents coded keyboard posting and PNG snapshots; neither API returns guest text or command completion. [Source: bridge.lua:393-404, 445-485](../../MCP/scripts/bridge.lua); [MAME natural keyboard](https://docs.mamedev.org/luascript/ref-input.html), [screen snapshots](https://docs.mamedev.org/luascript/ref-devices.html).

## 2. MAME/Lua hooks

Lua could observe a proven device output path, install an address-space tap, or watch emulated state. MAME documents read/write taps and post-load notifiers. Those mechanisms make event capture possible but do not identify an OS-9 shell stream automatically; the correct device, address, and mapping must be verified for the chosen image. Polling or tapping a presumed text buffer is especially fragile across screen modes and process/MMU changes. A hook should report raw observations with provenance, then a guest-level command marker can establish boundaries. [MAME Lua memory taps](https://docs.mamedev.org/luascript/ref-mem.html), [Lua notifiers](https://docs.mamedev.org/luascript/ref-common.html).

The current bridge is request/reply only. Streaming characters would require a bounded event queue or a new event path and a policy for overflow, reconnect, and load/reset. Hook use is MAME-specific; it is valuable for diagnosis or a tightly controlled image but a poor sole abstraction for future real hardware. [Source: bridge-server.ts](../../MCP/src/bridge-server.ts), [bridge.lua:502-634](../../MCP/scripts/bridge.lua).

## 3. Serial / UART transport

The MAME CoCo 3 driver currently declares an RS-232 port with a default printer device. That establishes an emulator device, not a ready OS-9 console or a UART in the MCP configuration. Before choosing this path, verify the exact MAME slot/endpoint options, guest driver, device descriptor, baud/framing, and whether a shell/login can be attached. The MCP would own a byte-stream endpoint and parse guest text independently of the display. [MAME CoCo 3 driver](https://github.com/mamedev/mame/blob/master/src/mame/trs/coco3.cpp).

This is attractive if real hardware parity matters. The command protocol would still need unique IDs and a verified completion marker or guest helper; simply receiving a prompt is insufficient when other processes can write to the same device. Serial links add byte loss, flow-control, and reconnect questions. A post-load reconnect must be treated as a new session until the guest proves readiness.

## 4. DriveWire / Becker-port transport

MAME's CoCo 3 driver instantiates a virtual Becker device. MAME's device source connects it to a DriveWire server over TCP and exposes a configurable port whose default is 65504. This is concrete applicability in MAME, but the current MCP launch does not start a DriveWire server or expose its virtual ports. [MAME CoCo 3 driver](https://github.com/mamedev/mame/blob/master/src/mame/trs/coco3.cpp), [MAME Becker device](https://github.com/mamedev/mame/blob/master/src/devices/bus/coco/coco_dwsock.cpp).

The pyDriveWire project documents Becker TCP mode, physical serial mode, and virtual serial channels. It also lists OS-9 /Z console windows among missing features in that implementation. Therefore, a DriveWire connection must not be equated with an available NitrOS-9 shell: the chosen guest image and server must prove a working console or dedicated command service. This path may share guest-level protocol concepts with real hardware while using a different physical host link. [pyDriveWire manual](https://github.com/n6il/pyDriveWire/blob/master/docs/The%20pyDriveWire%20Manual.md), [NitrOS-9 project](https://github.com/nitros9project/nitros9).

DriveWire may also serve disks. A machine save state does not, by itself, establish a matching external server connection or roll back host-served disk contents. Recovery must identify the server instance and disk baseline, reconnect, and prove the guest shell is responsive before accepting another command. MAME's Becker device source shows socket use and selected internal receive fields in its save-state registration; full socket/session restore behavior still needs a live test. [MAME Becker device](https://github.com/mamedev/mame/blob/master/src/devices/bus/coco/coco_dwsock.cpp).

## Shared readiness, timeout, and recovery rules

1. Treat MAME process alive, Lua bridge reachable, guest booted, and console ready as distinct states. A saved checkpoint should be taken only after the intended console has shown a verified ready signal.
2. Serialize commands per console. Associate captured bytes or observed screen intervals with one command ID. Keep command acceptance, completion, and transport health as separate observations.
3. Use bounded boot, ready, command, and restore deadlines. On timeout, preserve the last observation and report whether the guest is silent, the transport is disconnected, or MAME exited; do not claim the command failed merely because no prompt was seen.
4. After a scheduled MAME load, wait for a post-load signal if available, reconnect external transports, recheck mounted media and guest readiness, and only then mark recovery complete. MAME's save/load methods return before completion. [MAME running machine](https://docs.mamedev.org/luascript/ref-core.html).
5. Test restoration against a disposable disk image or a separately tracked disk baseline. The current state wrapper neither snapshots host disk bytes nor verifies external server state. [Source: tools.ts:428-458](../../MCP/src/tools.ts).

## Recommended staged approach

**Stage A — establish a reproducible boot and visual baseline.** Select one known NitrOS-9 image, verify its boot path and prompt from primary documentation and live MAME observation, then use keyboard plus screen capture only to prove boot, reach a known shell, and establish a checkpoint. This is the fastest way to expose boot and screen assumptions, but it is a bootstrap rather than the final text channel.

**Stage B — make a byte stream the command channel.** Prefer DriveWire/Becker if the chosen image and server demonstrate a dedicated guest console or virtual port in MAME; choose serial if that guest path is unavailable or real-hardware parity is the immediate priority. Define a small guest-visible command boundary contract with unique IDs and verified completion/status semantics. Keep the byte-stream adapter separate from the MCP command/session logic so the chosen transport can change.

**Stage C — make recovery observable.** Integrate post-load observation, transport reconnection, disk-baseline checks, and a fresh ready handshake. Keep screenshots and Lua hooks as independent diagnostics when the text channel fails. Do not promote a save-state load's scheduled response to a successful recovery.

Before choosing Stage B's transport, confirm the guest image's device drivers and shell routing, MAME's configured serial/Becker endpoint behavior, and the exact save/load behavior with mounted or host-served disks. These are explicit decision gates, not implementation tasks completed by this document.
