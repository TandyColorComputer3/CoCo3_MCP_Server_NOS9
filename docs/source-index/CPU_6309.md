## What the source demonstrates

**Observed in the source paths below:** FFork uses LDQ/STE and W-based transfers in H6309 branches. FMapBlk uses W instead of a stacked temporary. krnp2_ver101 tests MD trap flags. rel_beta6 explicitly selects native mode/FIRQ behavior; BASIC09 real arithmetic and RunB contain extended-register code.

## Dangerous, historical or version-specific patterns

Timing claims are source commentary, not benchmarks. LDMD/FIRQ changes and extended register frames affect the whole execution environment. SysCall deliberately uses the 6809 frame despite its filename. C opcode tables and binary language tags are not execution proofs. Evidence is in the entry-point files above; [the dependency audit](PROVENANCE_DEPENDENCIES.md) and [module comparisons](RUNTIME_MATCHES.md) record unresolved links.

## Critical distinctions

- `/dd/SOURCECODE/ASM/NITROS9/GIMEX/rel_beta6.asm:324` explicitly changes native/FIRQ behavior; surrounding comments say sound-driver work requires changes. Do not lift it into application code.
- `/dd/SOURCECODE/ASM/NITROS9/KERNEL/krnp2_ver101.asm:100` handles illegal-instruction/division traps. This is mode-sensitive kernel code.
- `/dd/SOURCECODE/ASM/BASIC09/syscall_6309.asm:20` forces the 6809 frame. Its filename is not evidence of 6309 optimization.
- `/dd/SOURCECODE/ASM/NITROS9/KERNEL/fmapblk.asm:22` has paired IFNE H6309/ELSE implementations; the source claims a speed motivation, not a measured Pass 2 improvement.
- `C/MAMOU/h6309.h`, `C/RMA/rtables.h`, and `C/RDUMP/6309dasm.c` contain instruction descriptions/tables. These are development-tool evidence, not executing 6309 guest routines.
- Live Clock2 has a 6809-object type tag and matches both `_6309` and `_6809` bundled files exactly. Conversely, a 6809-object tag on other modules does not prove no extended opcodes.
